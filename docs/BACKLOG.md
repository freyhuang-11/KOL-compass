## 2026-06-24 — 达人评估维度（履约率/出单率导向）

### 竞品
- **达秘**：很多机构在用「达秘」做达人建联。需对标其能力（建联效率、达人评估、批量能力等）。

### 商家核心诉求
商家最在意 **履约率** 和 **出单率**。评估一个达人值不值得建联/合作，会从这几个角度分析达人质量——**这些都该做成达人库里的评估指标/筛选维度**：

1. **达人最近 1 个月的内容相关性 + 购买意向信号**
   - 最近 1 个月的视频内容里**有没有出现相关商品**（品类匹配）。
   - **评论率**高不高。
   - 评论区**有没有人在问**（"哪买""多少钱"这类购买意向）。
2. **历史合作数据**：该达人**历史合作的相关数据**怎么样（带过的货、成效）。
3. **达人履约率**：接了合作真正产出/完成的比例。
4. **建联回复率**：批量发建联消息时，这个达人的**回复率**怎么样。

> 落地方向：把以上 1–4 做成达人库的评估列/评分/筛选，帮 BD 在建联前就判断达人质量，提升履约和出单。数据来源需先查 TikTok Partner API 能拿到哪些（评论、历史合作、履约等），**不假设**。

## 2026-06-28 — 多店铺「新增店铺」入口要显眼（UX 缺陷，要改）

B 端客户普遍**多店铺**，但现在"新增/绑定店铺"入口藏得太深、文字隐晦：
- 已绑一个店后，产品管理/达人库页只剩**店铺下拉选择器**，没有"新增店铺"按钮；要新增得绕到「平台设置」，而且那里叫**「管理授权 / 绑定店铺」**（隐晦，客户看不懂"授权"=加店）。
- 要改：① 在**店铺选择下拉旁边**永远放一个显眼的 **「+ 添加店铺」** 按钮（产品管理、达人库都要有）；② 文案从"管理授权/绑定店铺"改成**"添加店铺 / 授权新店铺"**这类直白词；③ 支持并清晰展示**多个已授权店铺**的切换与管理（解绑、重新授权）。
- 关联：当前 `startTikTokAuth`（app.js）只在 `shops.length===0` 时露"绑定店铺"按钮；多店铺场景没入口。对齐"单商家多店铺"定位。

## 2026-06-28 — 寄样走 API + 自动回复发图能力（待核实）

- **寄样走 API（核对+对齐）**：真实 TikTok 流程里寄样属于定向/公开计划——达人申请样品 → 商家审核 → 发货填运单。**很可能有对应 API，但具体端点未在 partner 文档核实到**（JS 渲染抓不到），且 Compass 的 messaging/collaboration 都还没接。现在寄样是**本地手动台账**，已（2026-06-28）**去掉手动新增**，只保留状态/运单更新。正式上线需：核实 TikTok 寄样/履约 API → 用 API 拉取样品申请、回写审核与发货状态，替换本地台账。
- **自动回复发图能力（核实）**：R9 给自动回复加了"图片回复"（语言无关、省翻译）。但**经 TikTok 私信/messaging API 是否支持发送图片消息未核实**。落地前需确认；若私信不支持发图，至少 Email 渠道可内嵌图片。

## 2026-06-27 — 自动接收达人回复（正式上线必备）

现在系统**只有出站**（我们发出去的私信/邮箱/定向邀约可见），达人的回复进不来——上一轮做的「手动登记」已去掉（措辞还误导说"没有接口"）。正式上线必须做**自动接收**：

- **TikTok 私信/站内信**：接 **affiliate messaging 收消息**能力（pull 轮询或 webhook）+ 会话列表，把达人回复自动落到对应会话、推进状态到「待我方处理」。文档：https://partner.tiktokshop.com/docv2/page/new-affiliate-messaging-apis （前提：messaging 发送先真正接通，目前 sandbox）。
- **Email**：客户邮箱现在只接了发信(SMTP)；要自动收回复需接 **IMAP 轮询**客户收件箱，按线程匹配回会话。
- 落地后：去掉/隐藏平台方「测试·模拟达人回复」，达人气泡「翻译成中文」按钮正式派上用场。

## 2026-06-27 — 翻译服务上正式前必须替换（阻断级）

现在翻译用的是 **MyMemory 免费 API**（无 key、无绑卡），额度是**全站/全客户共享**的（匿名约 5000 字/天）。

- **问题**：额度一旦用尽，**客户在产品里翻译时也会看到「额度已用完」**——上正式给客户用绝对不行。
- **上线前必须换成正式方案**，候选：
  1. 自建 **LibreTranslate**（开源、可私有部署、无第三方额度，单次成本＝服务器）；
  2. 商用翻译 API（DeepL / Google / 火山引擎等，按量计费、质量更好，但要绑卡/成本）；
  3. MyMemory 付费档（设 `MYMEMORY_EMAIL` 仅提到约 5 万字/天，仍是共享池，不算正式解法）。
- 倾向：**自建 LibreTranslate** 兜底 + 可选商用 API 提质，按成本和译文质量再定。
- 关联：当前免费实现见 `server.js` 的 `/api/translate`、前端「翻译成达人语言 / 翻译成中文」。
